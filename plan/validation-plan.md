# 検証計画 — 「本当に使いたいと思うのか」を確かめる

[事業計画](./business-plan.md) の前提は全部仮説である。このファイルは**それを壊しにいく**ための手順書。

原則:

1. **アイデアの説明をしない。** 相手の過去の行動を聞く（「使いますか？」ではなく「直近1ヶ月で何が起きたか」）
2. **褒め言葉はデータではない。** 「面白いですね」は情報量ゼロとして扱う
3. **数字と固有名詞を取る。** 「たまに困る」ではなく「先週2回」「ヤマトの再配達」
4. **否定が出たら成功。** 早く壊せたぶんだけ時間が浮く

---

## 1. 検証したい仮説（反証可能な形で）

| # | 仮説 | 反証条件（これが出たら仮説は死ぬ） | 検証方法 |
|---|---|---|---|
| H1 | 生活者は受取に実際のペインを持っている | 「直近1ヶ月で受け取れず困ったこと」が20人中5人未満 | 生活者インタビュー |
| H2 | 受取先を配送中に変えられることに価値を感じる | デモを触った後の利用意向が平均3.0未満（5点満点） | デモ＋アンケート |
| H3 | 「移動中の自分に届く」は受け入れられる | 位置共有への拒否感が過半数 | デモ＋アンケート（Q6不安） |
| H4 | **配送事業者は再配達コストを金額で持っている** | 5社中1社も数字を出せない | 事業者インタビュー |
| H5 | **その削減に対価を払う意思がある** | 「効果があっても払う仕組みがない」が支配的 | 事業者インタビュー |
| H6 | 個人は課金対象にならない | 個人の6割以上が有料でも使うと回答（＝この仮説が壊れる。歓迎すべき反証） | アンケートQ5 |

**H4とH5が死んだらこの事業は成立しない。** 最優先で検証する。

## 3. 生活者インタビュー・スクリプト（15分）

> 最初にアイデアを説明しないこと。説明は最後の3分だけ。

### Part 1: 過去の行動（7分）— ここが本番

1. 「ネットで物を買う頻度って、週どれくらいですか？」
2. 「**直近1ヶ月で**、荷物を受け取れなかったことはありましたか？」
   - あった → 「何の荷物でしたか？」「そのときどうしました？」「何回やり直しましたか？」
   - なかった → 「どうやって受け取れてるんですか？」（置き配？在宅？誰か家にいる？）
3. 「置き配は使ってますか？ 不安に思ったことは？」
4. 「冷蔵・冷凍のものはネットで買いますか？」
   - 買わない → 「なぜ買わないんですか？」（**受取が理由なら大きい**）
5. 「コンビニ受取やロッカー受取は使ったことありますか？ どうでしたか？」
6. 「受取のために予定を変えたことはありますか？」

### Part 2: 選好（3分）

7. 「もし冷凍食品を家以外で受け取るとしたら、どこなら許容できますか？」
   （コンビニ／駅／勤務先／友人宅／移動中の自分に手渡し）
8. 「その中で絶対に嫌なのはどれで、それはなぜですか？」

### Part 3: デモを触ってもらう（4分）

9. デモを渡して**何も説明せず**触ってもらう。観察するのは以下だけ。
   - 最初にタップした場所
   - 「拒否」が出たときの反応（納得したか、意味が分からなかったか）
   - 自分から例外を発生させてみるか
   - 声に出した言葉をそのまま記録
10. 触ったあとで検証タブのアンケートに回答してもらう（1分）

### Part 4: 最後の1分

11. 「これ、身の回りで一番刺さりそうな人って誰ですか？」（紹介につながる）

### 記録テンプレート

```
日付 / 相手の属性（世帯構成・勤務形態・EC頻度）
直近1ヶ月の受取失敗: 回数・荷物の種類・対処
冷蔵冷凍をECで買うか: Yes/No・理由
許容できる受取地点: / 絶対に嫌: 
デモで詰まった箇所:
そのまま記録した発言（1〜2個）:
アンケート回答ID:
```

## 4. 事業者インタビュー・スクリプト（30〜45分）

対象: 配送事業者（物流企画・支店運営）、マンション管理会社、EC物流担当

### 配送事業者向け

1. 「再配達の件数は、いまどう把握されていますか？」
2. **「再配達1件あたりのコスト、社内では何円で計算していますか？」**（← A-1。これが最重要）
   - 出てこない場合 → 「では、ドライバー1人の1日あたりの配達件数と、再配達に使っている時間の割合は？」（間接的に積む）
3. 「再配達を減らすために、いま何をやっていますか？ 効果は出ていますか？」
4. 「受取場所の変更機能は、利用者にどれくらい使われていますか？」
5. 「置き配の割合は？ 盗難やクレームはどれくらい発生していますか？」
6. 「冷蔵・冷凍の荷物の受取失敗率は、常温と比べてどうですか？」
7. 「他社のロッカーやコンビニに預けることに、抵抗はありますか？」（キャリア横断の受容性）
8. 「再配達が減ったとして、その効果はどの部署の数字として現れますか？」（誰が予算を持つか）
9. 「新しい仕組みを入れるときの意思決定は、誰がどの順番でやりますか？」
10. 「2030年に輸送能力が3割不足するという話について、社内ではどう捉えていますか？」

### マンション管理・不動産向け

1. 「宅配BOXの設置状況と、満杯になる頻度は？」
2. 「宅配に関する住民からの要望・クレームはどんなものがありますか？」
3. 「配送員の建物内への立ち入りは、いまどう管理していますか？」
4. 「配送ロボットが共用部に入ることについて、管理規約上の論点は何ですか？」
5. 「住民向けサービスとして、月いくらまでなら管理費から出せますか？」
6. 「設備投資の意思決定は誰がしますか（管理組合／デベロッパー／管理会社）？」

## 5. デモを使った行動観察

[デモ](../app/)は説明資料ではなく**計測器**として使う。見るのは次の4点。

| 観察点 | 何が分かるか |
|---|---|
| 最初に選んだ受取地点 | その人の本当の受取先選好（言葉より正確） |
| 「拒否」表示への反応 | 制約（温度帯・本人確認）が直感に合っているか |
| 自律レベルをどこに設定するか | AIへの委譲許容度。L4を選ぶ人がいたらリスク説明が届いていない |
| 例外を自分から発生させるか | 例外設計への関心度。ここに食いつく人は事業側の人 |

デモ内の検証タブで集めた回答は、イベント後に**CSV/JSONで書き出して**このリポジトリの外で分析する。
（回答はブラウザのlocalStorageに保存される。端末を変えると引き継がれないので、**同じ端末を人に渡して入力してもらう**運用にする。）

### 回答をサーバーに集めたい場合

`app/index.html` に以下を追加すると、回答が指定のエンドポイントにもPOSTされる。

```html
<script>window.LM_SURVEY_ENDPOINT = "https://example.com/collect";</script>
```

Google Formsの外部送信やFormspreeのようなサービスでも受けられる。
イベント当日にオフラインでも動くよう、localStorageへの保存は常に行われる。

## 6. 判断基準（Day 14）

| 結果 | 判断 |
|---|---|
| H4（コストの実数が出る）＋H5（払う意思）が両方立つ | **Go**: パイロット設計に進む |
| H4は立つがH5が立たない（効果はあるが払う仕組みがない） | **Pivot**: 課金先をマンション/不動産のSaaSに切り替える |
| H1が立たない（生活者にペインがない） | **Stop**: 前提が間違っている。AIエージェント × 物流の別の接点を探す |
| H2が立たない（動的変更に価値を感じない） | **Pivot**: 権限・証跡（責任分界）側に価値がある可能性。B2Bの監査用途へ寄せる |
| H3が立たない（位置共有が拒否される） | **縮小**: 「移動中の自分」を外し、固定Hub間の再ルートに絞る |
